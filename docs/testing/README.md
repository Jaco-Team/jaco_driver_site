# Проверки сайта

Доступные команды определены в [`package.json`](../../package.json):

```bash
npm run lint
npm run typecheck
npm test
npm run format:check
npm run build
```

Для изменения экранов обычно проверяют lint, typecheck и соответствующие unit-тесты. После изменений маршрутизации, авторизации, темы, `next.config.js`, service worker или переменных сборки нужен production build. Эти команды описывают порядок проверки; факт их прохождения нужно фиксировать отдельно для конкретного изменения.

## Актуальный прогон 16.10.2026: устаревшие ответы

На Node.js `24.15.0` прошли `npm run lint`,
`npm run typecheck -- --incremental false`, `npm run format:check` и `npm test`:
**82 файла / 620 тестов**, без падений, пропусков и todo. Все 580 тестов
предыдущего аудита сохранены, добавлено 40: три интеграционных воспроизведения
и 37 проверок обработчиков сессии и заказов.

Три интеграционных теста сначала воспроизвели ошибки на прежнем коде,
после исправления прошли:

- При переключении кафе А → Б → А старый ответ А больше не заменяет свежие
  заказы ни в состоянии интерфейса, ни в контекстном кэше, ни в `localStorage`.
- Успешный запоздалый `refreshSession` после явного выхода не возвращает
  прежнего пользователя и не снимает отметку выхода.
- Ошибка `401` старого `refreshSession` после входа в другой аккаунт не
  удаляет его токен и не сбрасывает новую сессию.

В `refreshSession` проверяются поколение сессии и исходный токен до любых
изменений данных, фильтра, кэша и состояния связи. Устаревший запрос возвращает
текущее состояние, а его завершение не выключает индикатор новой проверки.
Дополнительно проверены `403`, сетевые ошибки и `500`, повторный вход с тем же
токеном, начало/завершение входа и сохранение обычного офлайн-поведения.

Запросы заказов упорядочены отдельно для каждого кафе/категории. Основная
загрузка и фоновое заполнение кэша используют общий порядок; старые ошибки
не открывают окно и не переводят сайт офлайн. Ответ с изменившимся токеном
не применяется. Защита по токену заказов сама по себе не различает выход и
повторный вход с буквально тем же токеном; поколение сессии в этом изменении
добавлено только для `refreshSession`.

Полезные ответы другого контекста по-прежнему сохраняются в кэш. Очередь
обновления при многократных нажатиях, индикаторы и обычная загрузка сохранены
отдельными тестами; новых запретов на обновление заказов нет.

Оптимизированная сборка Next.js `16.4.2` прошла в отдельной временной копии
без реальных env/API, с отключёнными телеметрией и отправкой в Sentry.
Рабочие сборки, запущенные серверы и production не затрагивались; выкладки
не было. Зависимости и API/CSP-конфигурация не менялись, `npm audit` не запускался.
Ручные сценарии добавлены в [чек-лист](./release-checklist.md), но не отмечены
выполненными: автоматический прогон не заменяет браузерную проверку и не
означает устранение всех возможных гонок login/logout/SSO.

## Предыдущий аудит 16.10.2026: тесты и документация

На Node.js `24.15.0` прошли `npm run lint`,
`npm run typecheck -- --incremental false`, `npm run format:check` и `npm test`:
**81 файл / 580 тестов**, без падений, пропусков и todo. Все 466 тестов из
предыдущего аудита сохранены; добавлено 114 сценариев. Найденные при аудите
13 файлов с замечаниями форматирования приведены к стилю проекта.

Дополнено покрытие:

- Запоздалая загрузка настроек после успешного сохранения/сброса не меняет
  настройки, выбранное кафе и настоящий offline cache. Если сохранение
  не удалось, актуальный ответ загрузки по-прежнему применяется.
- Очередь обновления заказов при многократных нажатиях, медленном ответе,
  ошибке, уходе офлайн и смене кафе/категории; восстановление частичного
  фильтра после повторной загрузки модулей из настоящего `localStorage`,
  старый формат кэша и очистка при смене аккаунта/выходе.
- Смешанный выбор фото и видео, приоритет MIME над расширением,
  сохранность черновика и повторный выбор удалённого файла.
- Выбор оформления меток и сохранение настроек при светлой, тёмной и
  системной теме, включая повторное сохранение после смены темы устройства.
- Реальный порядок загрузки env в обоих этапах `preview:offline`, согласованность
  явно заданного API с CSP/proxy и запуск standalone из временной фиктивной
  сборки. Тесты не запускают настоящий сервер и не обращаются к рабочему API.
- Ошибки и 12-секундный тайм-аут авторизации `/api/offline-map/session`:
  сессия не выдаётся при неуспехе, повтор требует новой успешной проверки.

Регрессионный тест сначала воспроизвёл потерю сохранённого кафе: устаревший
ответ удалял ключ из `localStorage` ещё до проверки актуальности. Запись в
хранилище перенесена после этой проверки; поведение актуального ответа
с недоступным кафе сохранено отдельным тестом.

Оптимизированная сборка Next.js `16.4.2` проверена в отдельной временной
копии проекта, без реальных env и обращений к backend, с отключёнными
телеметрией и отправкой в Sentry. Рабочие `.next`/`.next-preview`, запущенные
серверы и production не затрагивались; выкладки не было. Зависимости в этом
этапе не обновлялись, повторный `npm audit` отложен.

Это автоматическая локальная проверка, а не браузерный smoke и не проверка
скачивания города против медленного API. Лимит авторизации скачивания
**остаётся 12 секунд**: тесты фиксируют безопасный отказ и повтор, а не
устраняют задержку. Визуальный контраст меток и полные онлайн/офлайн-сценарии
нужно проверять отдельно по [чек-листу](./release-checklist.md).

## Ручная локальная проверка

Офлайн-сценарии проверяют не в `next dev`, а через `npm run preview:offline`: dev-режим намеренно не регистрирует service worker. Откройте нужные страницы онлайн, дождитесь загрузки заказов и ресурсов карты, затем отключите сеть и повторите сценарии из [релизного чек-листа](./release-checklist.md). Для карты отдельно проверьте онлайн-рендерер и сохранённую офлайн-подложку.

Окна ошибок графика без реальных записей можно посмотреть на `http://localhost:3225/graph?uiPreview=1` при `npm run dev`. Режим доступен только на `localhost` в development-сборке, показывает локальные тестовые данные и не отправляет обжалования. В `preview:offline` и релизе он недоступен; для финальной проверки реальных данных используйте тестовый аккаунт.

Page-тесты лежат в [`tests/pages/`](../../tests/pages), тесты моделей и UI — рядом с соответствующим кодом. Тестовые файлы не помещают в `pages/`, иначе Next.js может принять их за маршруты.
