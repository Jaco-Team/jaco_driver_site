# Локальная разработка

## Запуск

Нужен Node.js версии, указанной в [`package.json`](../package.json) (`>=24.15.0`).

```bash
npm install
npm run dev
```

Dev-сайт доступен на `http://localhost:3225`. Основные команды:

| Команда                                             | Назначение                                                 |
| --------------------------------------------------- | ---------------------------------------------------------- |
| `npm run dev`                                       | Next.js с HMR                                              |
| `npm run build` / `npm run start`                   | Production-сборка и сервер                                 |
| `npm run preview:offline`                           | Сборка и локальный standalone-preview для проверки офлайна |
| `npm run lint` / `npm run typecheck` / `npm test`   | Статические проверки и unit-тесты                          |
| `npm run format:check`                              | Проверка форматирования                                    |
| `npm run deploy:local`, `deploy:dev`, `deploy:prod` | Legacy PM2-сценарии; не нужны для локальной разработки     |

Service worker отключён в `next dev`: кэширование изменяемых HMR-ресурсов приводило к устаревшему коду и перезагрузкам. Офлайн-поведение проверяйте через `npm run preview:offline`; команда собирает приложение и запускает standalone-сервер на том же порту.
Preview собирается отдельно в `.next-preview`, поэтому не перезаписывает dev-сборку. Если dev уже занимает порт 3225, запустите preview на другом: `PORT=3325 npm run preview:offline`. При наличии сети онлайн-карта заказов в preview использует API 2.1; при её отключении — сохранённую офлайн-подложку.

`preview:offline` использует те же локальные настройки, что и `dev`: внешние переменные окружения имеют приоритет, затем читаются `.env.development.local`, `.env.local`, `.env.development` и `.env`. Сборка и standalone-сервер получают один набор настроек; `NODE_ENV` остаётся `production`, чтобы service worker работал. `.env.production.local` в этом локальном сценарии не подмешивается. При отсутствии корректного `NEXT_PUBLIC_API_ORIGIN` (или `NEXT_PUBLIC_API_URL`) команда останавливается с пояснением, а не переключается молча на рабочий API. Обычные `build`, `start` и команды развёртывания не изменены.

После изменения env остановите сайт и снова выполните `npm run preview:offline`: готовую сборку нужно пересобрать. Для проверки сначала откройте `http://localhost:3225` с сетью, войдите и скачайте город, затем отключайте сеть. Backend должен оставаться запущенным для входа и скачивания карты.

`dev` и `preview:offline` запускают сайт локально; адрес backend задаёт env,
а не название команды. Для обычной локальной работы и проверки офлайна
PM2-команды `deploy:*` не используются. Настройка боевого окружения и его
развёртывание не входят в этот локальный процесс.

Скачивание города работает и в `dev`: service worker нужен для открытия
страниц без сети, а не для сохранения тайлов. Если `/api/offline-map/session`
отвечает `502`, проверьте состояние локального API
и текст ответа. Серверная проверка авторизации перед скачиванием ограничена
12 секундами независимо от режима запуска; этот лимит не увеличен локальным
тайм-аутом входа. Переключение на preview само по себе не устраняет задержки
backend. Кэш скачанных карт ради этой диагностики удалять не нужно.

## Обновление зависимостей

После изменения `package.json` выполните `npm install` и сохраните `package-lock.json`. Файлы MapLibre для офлайн-карты синхронизируются с установленным пакетом автоматически перед `dev`, `win` и `build`; отдельно доступна команда `npm run sync:offline-map`. Она обновляет ссылки на модули, CSS и версии кэша, не удаляя скачанные карты городов. Повторный запуск без изменений ничего не перезаписывает. В Docker синхронизация выполняется на этапе сборки, когда исходники уже скопированы.

В `overrides` закреплены исправленная версия gRPC для Firestore и замена `fast-glob` на `tinyglobby` только внутри ESLint-плагина Next.js. Это устраняет уязвимые транзитивные зависимости без отката Firebase и Next.js. Совместимость определения каталогов Next.js проверяется в `tests/tooling/next-eslint-glob.test.mjs`; при обновлении плагина нужно пересмотреть override и эти тесты.

### Обновление 16.10.2026

Обновлены Next.js / `eslint-config-next` до `16.4.2`, React / React DOM до
`19.3.1`, MUI до `9.5.0`, Date Pickers до `9.15.0`, Sentry до `11.8.0`, Firebase
до `13.0.0`, MapLibre до `6.14.0`, Sass до `1.105.2`, Prettier до `3.9.10`,
jsdom до `30.1.3`, Vite до `8.3.4` и Vitest до `5.0.5`. В `overrides`
обновлены PostCSS до `8.5.30` и gRPC до `1.14.6`; `source-map-js` и локальная
замена `fast-glob` сохранены.

У MapLibre `6.14.0` production-модули самостоятельные, а
`maplibre-gl-shared.mjs` пустой. Скрипт синхронизации поддерживает как этот
формат, так и прежние модули с общим кодом. Нельзя просто убирать проверки
структуры пакета: пустой общий файл, на который осталась ссылка, по-прежнему
считается ошибкой. Версии ресурсов, загрузчика и service worker меняются
согласованно; имя кэша скачанных тайлов сохраняется. Повторная синхронизация
без изменений ничего не перезаписывает.

Firebase обновлён как npm-пакет. Старый `public/firebase-messaging-sw.js`
загружает собственный SDK с CDN и не использует установленный пакет; его
миграция не выполнялась. Обновление npm-пакета не подтверждает исправность
этого старого обработчика уведомлений.

### Почему пока ESLint 9 и TypeScript 6

На 16.10.2026 оставлены ESLint `9.39.5` и TypeScript `6.0.3`. Переход на
ESLint `10.12.0` / TypeScript `7.0.2` требует отдельного решения по инструментам:

- `eslint-config-next` подключает `eslint-plugin-react@7.37.5`,
  `eslint-plugin-import@2.32.0` и `eslint-plugin-jsx-a11y@6.10.2`. Эти плагины
  пока заявляют совместимость с ESLint не выше 9, в том числе в своих актуальных
  npm-релизах.
- `typescript-eslint` поддерживает TypeScript `>=4.8.4 <6.1.0`, а не 7.
  Ограничение проверено и для актуального релиза `8.71.2`; оно описано в
  [официальной документации](https://typescript-eslint.io/users/dependency-versions/).

При следующем обновлении нужно повторно проверить поддержку. Не отключать
правила и не менять плагины без согласования ради новых номеров версий.
Существующий `legacy-peer-deps=true` в `.npmrc` нужен для обёртки Яндекс Карт,
заявляющей поддержку React до 18; он не доказывает совместимость остальных
пакетов. Поэтому успешной установки недостаточно: нужны проверки кода, типов,
тесты и сборка.

## API и переменные окружения

Имена параметров перечислены в [`.env.example`](../.env.example). Реальные настройки всех окружений хранятся в OpenBao; `.env.development` и `.env.production` удалены из Git. Для локальной разработки используйте приватный `.env.development.local`, который исключён из Git и Docker-контекста. Основные параметры: `NEXT_PUBLIC_API_ORIGIN`, `NEXT_PUBLIC_API_PROXY`, `NEXT_PUBLIC_MEDIA_ORIGIN`, `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` и параметры Sentry. Серверный `YANDEX_TILES_API_KEY` не должен попадать в `NEXT_PUBLIC_*`; подробности — в [документе о карте](./maps.md). Production-процесс описан в [развёртывании через OpenBao](./deployment-openbao.md).

Обычный `npm run dev` использует адрес API из env. Для отдельного запуска с локальным backend, например на порту 8080:

```bash
NEXT_PUBLIC_API_ORIGIN=http://localhost:8080 NEXT_PUBLIC_MEDIA_ORIGIN=http://localhost:8080 NEXT_PUBLIC_API_PROXY=true npm run dev
```

Если backend не разрешает CORS для dev-сайта, установите `NEXT_PUBLIC_API_PROXY=true`: браузер обращается к `/api/v1/*` на том же origin, а Next.js перенаправляет запросы на `NEXT_PUBLIC_API_ORIGIN`. Другой вариант — настроить CORS на backend. После изменения env перезапустите dev-сервер. `NEXT_PUBLIC_*` встраиваются при сборке: смена их значений только при запуске уже готового standalone-сервера не изменит клиентский код.

Настройка Docker и серверных секретов — в [Docker-инструкции](./docker.md).
